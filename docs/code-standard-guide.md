# 小刻食堂组开发流程与规范文档

## 📂 分支管理规范

### 1. 分支命名

| 分支类型 | 命名格式           | 使用场景说明                              |
| -------- | ------------------ | ----------------------------------------- |
| `feat/`  | `feat/<功能简述>`  | 新功能开发（例：`feat/user-login`）       |
| `fix/`   | `fix/<修复简述>`   | 已有功能问题修复                          |
| `test/`  | `test/<测试内容>`  | 专项测试（如性能/压力测试或者预发布检查） |
| `chore/` | `chore/<维护内容>` | 日常维护（依赖更新/配置文件调整）         |
| `perf/`  | `perf/<优化内容>`  | 性能优化（如代码重构/算法优化）           |

:::caution 命名内容要求

- 应尽量简洁明了
- 非常完全尽可能使用英文
- 使用`-`连接单词

:::

### 2. 分支策略

- `master` 分支受保护，​**禁止直接push**
- 新功能需从`master`创建分支开发
- `dev` 分支用于部署测试环境，不受保护
- `dev` 更新后会自动部署到测试环境，如遇到分支崩溃，删掉从主分支重新拉取（客户端可能没有这个分支）
- `test`分支用于测试，不会合并到`master`分支

:::tip 分支功能与合并
每个分支的功能应做到单一，不要混合多个功能。对于多个功能的需求，应该分别开发不同的分支。  
如果有相互依赖的功能，可以在pr中指向依赖的分支，在所依赖的分支合并后，Github 会自动 rebase 本分支。  
因此对于链式依赖的功能，应该按照依赖关系顺序，从最接近`master`的分支开始合并。
:::

## ✨ 提交信息规范

- 使用 ​**Gitmoji** 开头（参考：[https://gitmoji.js.org/](https://gitmoji.js.org/)）
- 格式：`:emoji: 提交描述`  
  (例: `✨ 新增用户登录界面`)

## 🚀 环境与部署（后端与网页）

| 环境      | 部署方式                | 对应分支 |
| --------- | ----------------------- | -------- |
| 正式环境  | 通过手动打tag触发       | master   |
| 测试/开发 | 合并到dev分支后自动部署 | dev      |

## 🚨 部署前注意事项

- 如果新增项目**配置字段**, 群里联系将配置加入线上环境变量后再发布

### Tag使用规则

- 仅在`master`分支打tag（格式：`v1.0.0`）

## 🔀 代码合并流程

1. 本地开发 -> push到远端仓库
2. 创建Pull Request到master分支
   - feat、hotfix类型PR需要有单元测试并通过 ✅
   - 需至少1个Reviewer批准 ✅
   - 需通过所有Checker检查（CI/CD）
3. PR合并后自动：
   - 删除原分支 🗑️
